# Internal exploration

The purpose is to preserve the lead's context for architectural judgment,
synthesis, planning, and steering: explorers absorb context-heavy navigation and
raw source or document reading, then return distilled, anchored evidence. The
lead retains exploration ownership and decides when evidence is sufficient;
small workers do not take over architecture or planning. Default to delegating
context-heavy gathering when it helps, while keeping a tiny direct read when it
saves overhead or context.

When Conductor is explicitly invoked for authorized planning or exploration, the
orchestrator may automatically dispatch bounded, read-only context gathering
before downstream stage settings are settled. Help and bare usage remain
non-dispatching. Exploration is discretionary: read a tiny known excerpt
directly when that better preserves context than fanout.

The lead chooses explorer model, supported effort, and count without routine
user questions, within host capacity and explicit user limits. Explorers gather and distill evidence; they never edit product files or become
implementers, reviewers, or fixers by relabeling. The lead decides architecture,
synthesizes reports, and stops when the requested answer or plan has sufficient
evidence. Explicit
user model, backend, budget, and concurrency constraints always win. Normal
user-facing settings for planning, implementation, review, fixes, and a requested
independent verifier still require complete setup before those stages proceed.

Prefer the smallest available adequate native worker and supported effort. As
conditional preference examples, consider Luna or Sonnet 5 at low/medium,
Haiku at max, or GPT-5.4-mini at medium/high; these are not portable IDs or
availability claims. Use weaker workers for exact locations and excerpts, and
stronger small workers for tracing behavior or synthesis. Pass minimal
task-specific context rather than routine full-history forks. Unsupported examples
permit another compatible supported choice; do not invent a cross-provider
ladder or use an external CLI merely to obtain a preferred name. If native
dispatch is unavailable, existing backend fallback rules apply and any selected
exploration model/effort may be passed explicitly when supported. If no useful
worker exists, read narrowly where permitted or report the constraint.

Independent focused questions may run in parallel within host capacity and user
limits. Exploration count is separate from implementation, reviewer, and fixer
caps; avoid unfocused or duplicate exploration. Reuse workers for related
follow-ups and reuse the agent-dispatch brief and status contract. Request
bounded evidence with path/line anchors, minimal excerpts, uncertainties, and
searched locations when something is not found. The lead assesses report
uncertainty before relying on it. Follow up or add areas only when reports leave
a material gap; stop when enough evidence exists for the requested answer or
plan, and report unavailable evidence explicitly.
